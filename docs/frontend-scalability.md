# Frontend scalability contract

The public site has two deliberately separate data paths:

- Default views use small JSON artifacts generated by Rust. They do not fetch the browser data index, Parquet, or WebAssembly.
- Custom views fetch `/browser-data/index.json`, select entries for exactly one wiki, verify each partition's byte length and SHA-256, and then decode those partitions with `parquet-wasm` and Apache Arrow.

## Publication layout

`wiki-econ merge` writes `browser-data-index.json` from the immutable per-wiki metric outputs. Each entry records the metric, wiki, minimum and maximum date, public file path, rows, bytes, and SHA-256. The site build copies only indexed sources into its staged release and publishes the index with the rest of that atomic release.

The current custom-query metrics are bounded monthly or yearly aggregates, so one file per metric/wiki is comfortably within the browser budgets. `page_weekly_edits` is intentionally excluded: it supplies a Rust-generated default page and is never decoded in the browser. If a per-wiki aggregate later exceeds the budgets, introduce a new index schema with year or bounded-range shards and retain the same selected-wiki loading contract.

## Browser cache

IndexedDB stores verified compressed Parquet bytes rather than expanded JavaScript objects. Cache keys contain both the cache schema version and content SHA-256. Writes are best-effort: quota errors, private-mode restrictions, blocked upgrades, and transaction failures never break a dashboard query.

The cache is capped at 96 MiB. Before a write, stale schemas are removed and least-recently-used entries are evicted until the new entry fits. A partition larger than the entire cache budget is decoded normally but not cached. In-memory decoded rows are retained only for the currently selected wiki.

## Enforced budgets

The source of truth is [`config/browser-performance-budgets.json`](../config/browser-performance-budgets.json). CI builds deterministic aggregate fixtures with 6,000 rows per metric for nlwiki, 3,000 for ptwiki, and 21,000 for frwiki (3.5× nlwiki), then drives the real production site in headless Chrome with a constrained JavaScript heap.

CI fails if:

- the default view requests the browser index, Parquet, or WASM;
- a custom view requests a partition for an unrelated wiki;
- loaded rows differ from the index;
- peak browser-memory headroom falls below 25%;
- total or per-1,000-row interaction latency exceeds the budget;
- a warm IndexedDB query downloads Parquet again;
- IndexedDB's configured ceiling drifts;
- an unexpected or oversized JavaScript/WASM chunk appears; or
- any DuckDB browser asset appears.

The performance report is retained as a CI artifact for trend review.

## DuckDB-WASM decision

DuckDB-WASM is not part of the current browser closure. The deterministic reference run on 2026-08-23 decoded the frwiki-sized GDP fixture (63,000 rows across three partitions) in approximately 164 ms with about 96.9% measured peak-heap headroom. This leaves no demonstrated bottleneck that justifies adding DuckDB-WASM's download, memory, and supply-chain cost.

If custom query shapes later exceed the budgets, evaluate DuckDB-WASM with an A/B fixture using the same files, filters, browser, cold/warm cache states, peak-heap sampling, and artifact accounting. It should be introduced only if that measurement shows a material improvement after including its own load and initialization cost.
