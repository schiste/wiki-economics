# wiki-economics — Full Repository Audit

**Date:** 2026-09-30 · **Commit:** `8b87839` · **Method:** static read-only analysis, 5 parallel deep-dives + independent verification of every blocker against source.

## 1. Verdict

**Overall grade: C+ (Solid safety architecture, unsound resource envelope)**

This is an unusually disciplined codebase in the places that are hardest to get right —
publication atomicity, artifact provenance, determinism contracts, supply-chain hygiene. It is
also **inconsistent with its own stated hard constraint** in the one place that constraint
exists to protect: the 6 GiB per-job memory ceiling.

The paradox: the publication path is defended with 16 fail-closed gates, cryptographic
receipts, and a 9-state recovery machine — while the memory governor that decides whether a
job survives at all is wired into 2 of 7 stages, defaults to a ceiling **2.67× the cgroup kill
boundary**, and is expressed as free-standing literals in six places while the canonical
`config/toolforge-capacity.json` is never read by Rust at all.

Read `config/toolforge-capacity.json:37` — `"assume_future_capacity_increase": false`. Then read
`src/resource_governor.rs:28` — `const DEFAULT_MEMORY_CEILING_BYTES: u64 = 16 * GIB;` — and the
shell comment at `deploy/toolforge/run-refresh.sh:109` that says verbatim
*"the pipeline must not assume an unavailable 16 GiB profile."* The codebase contains the exact
value its own policy forbids, as a live fallback.

Derived from `config/toolforge-capacity.json` and `deploy/toolforge/jobs.yaml`:

|---|---|---|

Two hard facts follow, and both are load-bearing for the grades:

1. **The fleet saturates the worker budget to the byte.** 4 fleet workers (2+2+6+6 GiB) leased
   = 16 GiB. The 1 GiB fleet-controller is *not* leased. 16 + 1 = **17.00 / 17.00 GiB — zero
   headroom**, and the 1 GiB that is consumed is invisible to the ledger.
2. **`config/toolforge-capacity.json` is read by exactly zero lines of Rust.** It is consumed by
   three Node scripts only. Every Rust and shell statement of the 6 GiB limit is a hand-copied
   literal that can drift — and one already has.

## 4. Blockers (P0) — fix before the next production run

### P0-1 · The memory governor defaults to 16 GiB in a 6 GiB world
`src/resource_governor.rs:28,68`
```rust
const DEFAULT_MEMORY_CEILING_BYTES: u64 = 16 * GIB;
...
    .unwrap_or(DEFAULT_MEMORY_CEILING_BYTES);
```
Reached when neither `WIKI_ECON_MEMORY_CEILING_BYTES` nor a readable `/sys/fs/cgroup/memory.max`
is available. The detection path (`src/observability.rs:126`) is **cgroup-v2 only** — while
`capture_page_cache` in the same file *does* have a v1 fallback, so v1 is a scenario the authors
anticipated. On v1, or if any wrapper forgets the export, every memory gate silently becomes a
no-op and the cgroup OOM-kills the job while the governor reports headroom.

**Fix:** delete the fallback — fail closed when neither source is available. Add a v1 fallback
(`/sys/fs/cgroup/memory/memory.limit_in_bytes`, rejecting the `LONG_MAX` sentinel). This is ~5
lines and removes the single largest correctness hazard in the repo.

### P0-2 · `config/toolforge-capacity.json` is never read by Rust; 5 copies of 6 GiB drift freely
Verified: `grep -rn toolforge-capacity src/` → **zero hits**.

| Value | Locations | Drifted? |
|---|---|---|
| `6442450944` (6 GiB) | `toolforge-capacity.json:5` (canonical), `capacity-qualification.json:3`, `run-refresh.sh:110`, `run-prepare-wiki.sh:39`, `run-qualify-wiki.sh:137`, `run-fleet-worker.sh:38` | **yes — see P0-1** |
| `1610612736` (1.5 GiB reserve) | 4 wrappers | no |
| `4000` millicores (per-job CPU) | config only | **never consumed by anything** |
| `25` (min headroom %) | `capacity-qualification.json:4`, `run-capacity-benchmark.sh:136`, `cpu_qualification.rs:326`, `qualify-capacity.cjs:45` | 4 copies |
| `DEFAULT_MAX_LOGICAL_PARTITION_BYTES = 8 GiB` | `resource_governor.rs:31`, `run-refresh.sh:118` | **8 GiB > 6 GiB job** |

**Fix (2 layers):** (a) have `capacity-admission.cjs` export `WIKI_ECON_MEMORY_CEILING_BYTES` and
`WIKI_ECON_MEMORY_RESERVE_BYTES` from the config into the child env (it already injects
`WIKI_ECON_CAPACITY_ADMITTED` at `:236`) and delete the 6 shell literals; (b) `include_str!` the
config in Rust and assert `memory_ceiling_bytes <= per_job_memory_limit_bytes` at
`ResourceBudget` construction. Then add a CI test asserting the shell wrappers and the JSON agree.

### P0-3 · The page-week monthly reduction — largest allocation in the pipeline — has no admission and uses the in-memory engine
`src/compute/weekly/mod.rs:399-425` does a full in-memory `group_by` + `.collect()`; the file
contains **0** `collect_with_engine` calls against 12 plain `.collect()`. Its only protection is
`validate_logical_partition` (`:357`), which compares **compressed on-disk Parquet bytes** against
an 8 GiB cap — larger than the entire job. 8 GiB of Zstd Parquet hash-aggregates to 20–40 GiB.

Verified governor wiring per file:

| file | governor references |
|---|---|
| `src/compute/weekly/mod.rs` | **38** |
| `src/compute/lifecycle/mod.rs` | **0** |
| `src/compaction.rs` | **0** |
| `src/merge.rs` | **0** |
| `src/patrol.rs` | **0** |
| `src/dashboard.rs` | **0** |
| `src/ingest.rs` | **0** |

`metrics`, `lifecycle`, `patrol`, `publish` and `site` run with zero memory admission.

**Fix:** (1) `.collect_with_engine(Engine::Streaming)` at `weekly/mod.rs:423` — the sibling paths
already use it (`compute/mod.rs:293`, `lifecycle/mod.rs:637`); (2) change the partition gate from
bytes to rows against `memory_admission_bytes()`; (3) thread a `&ResourceGovernor` into
`compute_all_incremental_cached` and `lifecycle::compute_external` — the call chain is short.

### P0-4 · The production capacity gate rejects every report the current binary emits
`src/capacity.rs` writes `schema_version: 5`; `scripts/qualify-capacity.cjs:82` demands `!== 3`.
The enwiki "fits in 6 GiB" mechanism is **structurally dead** — every report is rejected before any
memory evidence is examined.

Worse, the two gates are mutually exclusive: `qualify-capacity.cjs:47,87` require `policy.cpu === 1`
**and** `report.rayon_threads === policy.cpu`, while `cpu_qualification.rs:366-374` requires
`profile.cpu > 1 && speedup >= 1.15`. The enwiki evidence chain cannot satisfy both.

**Fix:** bump the JS gate to `!== 5`, then reconcile the single-CPU constraint with the Rust
multi-CPU requirement. Small, but this is the gate that unblocks enwiki.

### P0-5 · 12 of 64 Node test files never run in CI — including the whole capacity-admission suite
**Status: FIXED in PR #105.** Verified by set difference against `.github/workflows/ci.yml:150-201`:

```
account-cohorts.test.mjs            admin-console.test.mjs
admin-dispatcher.test.cjs           admin-operation-policy.test.cjs
admin-operation-status.test.cjs     build-admin-site.test.cjs
capacity-admission.test.cjs         editor-identities.test.mjs
machine-api.test.cjs                metric-parity.test.mjs
pipeline-state.test.cjs             run-compatibility-cohort.test.cjs
```

`capacity-admission.cjs` — the component that enforces the 17 GiB ledger — and
`pipeline-state.cjs` — the coordinator that enforces stage concurrency — have **zero executed
coverage in any gate**. All 12 are in `scripts/ci-local.sh`, so a contributor running the
documented local gate gets them; CI does not.

**Fix (one line, highest leverage in the whole report):** replace the 52 explicit invocations
with a glob:
```yaml
node --test 'site/**/*.test.cjs' 'site/**/*.test.mjs' 'scripts/**/*.test.cjs' 'deploy/**/*.test.cjs'
```
This closes the blocker and makes the class of bug structurally impossible.

### P0-6 · A public, unauthenticated endpoint's memory cap equals the entire pod limit
`site/machine-api.cjs:42-43`
```js
const MAX_METRIC_SOURCE_BYTES = 512 * 1024 * 1024;   // == resident_service_memory_bytes, exactly
const MAX_METRIC_SOURCE_ROWS = 2_000_000;
```
Compounding: `new Uint8Array(fs.readFileSync(...))` **copies** the buffer (2× peak); the row cap is
checked *after* `table.toArray().map(...)` has already materialised every row; the cache holds 8
such arrays with no byte accounting; every request re-materialises a full deep copy even on a cache
hit; MCP allows 64 messages × 20 aggregations = 1 280 full passes per request. Rate limiting does
not help — the bucket keys on a caller-supplied `x-forwarded-for` (`:266-273`).

**Fix:** `64 MiB` source cap; read only the Parquet footer and reject on row count *before*
`toArray()`; drop the `new Uint8Array(...)` copy; replace the count-8 cache with a 32 MiB
byte-budgeted one; return cached rows without recopying.

## 5. Majors (P1)

### P1-1 · No `isolated` fleet worker exists — enwiki tasks can never be claimed
`grep -c isolated` → **0** in both `jobs.yaml` and `run-fleet-worker.sh`, which accepts only
`small|medium_large` (`:17`). But `toolforge-capacity.json:15` budgets 6 GiB for an `isolated`
class, `capacity-admission.cjs:221` accepts it, and `config/fleet-qualification.json:52` defines
an `enwiki_isolated` step that **cannot be executed**. Meanwhile `fleet.rs:235-240` forces monthly
layouts to `Isolated` — so an enwiki task is classified into a class no worker can serve.

**This is the concrete answer to "what blocks enwiki."** Not the capacity arithmetic — that is
correct. `src/compute/mod.rs:2028` (`if wiki == "enwiki"`) already routes enwiki to bounded
sequential family passes with the right rationale. What's missing is a job that can run them.

### P1-2 · `ChurnAccumulator.seen` is O(editors × months) and never cleared
`src/compute/lifecycle/mod.rs:60-65`
```rust
pub(super) struct ChurnAccumulator {
    period_type: &'static str,
    seen: HashSet<(i64, i32)>,
    ...
}
```
`observe` (`:77-78`) inserts `(user_id, period_key)` and returns early if already present — the set
is never pruned, so it grows to **distinct editors × all months in the analysis window**. At enwiki
scale that is 15–30 GiB in a 6 GiB job, and this is in `lifecycle`, which has **zero** governor
wiring (P0-3). This is the most likely enwiki OOM, and it is a data-structure problem, not a
tuning problem.

### P1-3 · 4 GiB of scheduled jobs are outside the capacity ledger
| job | jobs.yaml | mem | ledger |
|---|---|---|---|
| `wiki-econ-fleet-controller` | `:45` | 1 GiB | unreserved, no lease |
| `wiki-econ-artifact-scrub` | `:118` | 2 GiB | `scrubber` class declared, never requested |
| `wiki-econ-fingerprint-check` | `:130` | 1 GiB | **no class at all** |

Declared total **26.5 GiB** against a **24 GiB** namespace. The ledger's 17 + 6.5 + 0.5 = exactly
24 GiB leaves zero room for these. On the 15th, scrub (05:00) + controller + fingerprint-check +
two medium workers can all be co-resident → k8s evicts.

### P1-4 · A hard-killed publisher blocks publication for up to 6 hours, invisibly
`run-publish-ready.sh:48` → `WIKI_ECON_PUBLICATION_LOCK_STALE_SECS:-21600` against a 60 s
heartbeat. A hard kill freezes `owner.json`; the +2 h and +4 h ticks both refuse; only at +6 h can
a successor steal it. Worse, `run-with-lock.sh:118-123` exits 75 **before** `run-record.cjs` runs,
so the skipped tick leaves *no run record at all* — invisible except in the Toolforge job log.

**Fix:** drop the stale window to ~15 min (the 60 s heartbeat plus the double-check recheck is
sufficient), and emit a `skipped: lock busy` run record before exiting.

### P1-5 · Oversubscription: 4 reconcile workers × a 4-thread Polars pool on a 4-vCPU quota
`resource_governor.rs:149-163` validates each external thread pool *individually* against
`thread_limit` and **never sums them**. `run-refresh.sh:55-69` sets `THREAD_LIMIT=4`,
`WEEKLY_WORKERS=4`, `MAX_ACTIVE_PARQUET_WRITERS=32` → 4 scoped workers
(`weekly/mod.rs:1786`) each running `group_by`/`sort`/`collect` on the shared 4-thread Polars pool
= **≥8 runnable workers on 4 vCPUs**. Also, `thread_limit` is env-driven only — the cgroup CPU
quota is parsed in `capacity.rs:244-253` but **never used to size a pool**.

**Fix:** add a `total_concurrency` invariant to `ResourceBudget::validate`; derive `thread_limit`
from `/sys/fs/cgroup/cpu.max` when the env var is unset.

### P1-6 · The governor's sampling cost is O(scratch files) and runs 2 000+ times per stage
`resource_governor.rs:539-545` calls `directory_bytes` (a full recursive walk) on every sample.
The scratch root is `output_dir.join(wiki)` — the **entire per-wiki output directory**, because
`WIKI_ECON_SCRATCH_DIR` is exported by only 2 of 7 wrappers. With ~2 500–4 500 files in the run
dir and 64×32=2 048 reconcile checkpoints, that is **5–9 M `stat()` calls on Toolforge NFS per
stage**. `append_weekly_bucket_results` adds ~2 048 more full scans. At ~1 ms per `stat` this is
hours of metadata I/O — a wall-clock failure mode invisible in the memory telemetry.

**Fix:** scope the scratch root to the run directory; cache `size_bytes()` incrementally; export
`WIKI_ECON_SCRATCH_DIR` for every stage.

### P1-7 · The no-op publication fast path performs zero byte-level re-authentication
`src/publication.rs:4156-4171` compares only `fs::metadata` size + mtime. No
`artifact_receipt::read`, no `verify`, no sha256. And `publish-ready-transaction.sh:97-102` then
**exits 0 without invoking the site build**, so `publication-verify` (the strongest gate) never
runs. A published Parquet corrupted in place with size and mtime preserved is republished
indefinitely. This contradicts `docs/stage-fingerprints.md:174-176`.

**Fix:** replace the closure with `artifact_receipt::verify(path, name, expected_sha, Fast)` —
one sidecar read per artifact (~15 files), no Parquet I/O. Bounded blast radius today only by the
monthly scrub (`:121`).

### P1-8 · `publication.rs` is 14 824 lines with 7 responsibilities and ~7 600 lines of tests
Owns candidate planning, ready-index management, qualification promotion, three retained
migrations, the gate, the recovery state machine, preflight, and retention. `publication::validate`
alone is 366 lines — and its drift gate is `#[cfg(all(not(test), not(coverage)))]` (`:6812-6824`),
so **the strongest publication invariant is disabled in exactly the two builds that would test it**.

Also: **17 hand-rolled atomic writers**, 2 of which use PID-only temp names
(`fingerprint.rs:781`, `generation_lifecycle.rs:264`) — and Toolforge pods report *identical PIDs*
(see the explicit comment at `run-fleet-worker.sh:80-82`), so those two can collide.

### P1-9 · A contributor's first hour is the slowest possible hour
**Status: PARTIALLY FIXED in PR #105** — the "Fast Inner Loop" section is added; the duplicated
`cargo test` in `ci-local.sh` is not yet removed.
`scripts/ci-local.sh` ≈ 30–70 min warm, and there is **no documented inner loop** — neither
`docs/development.md` nor `CONTRIBUTING.md` mentions `cargo test --locked <module>` or
`node --test site/<name>.test.cjs`. It also runs `cargo test` *and* `cargo llvm-cov` (the full
suite twice — CI drops the former for exactly this reason), and omits shellcheck, which CI enforces.
Given "agility" is a stated goal, this is a first-order problem, and the fix is ~10 lines of docs.

### P1-10 · CI can ship an attested release with zero Rust tests
`ci.yml:452` accepts `coverage.result == 'skipped'`, and `coverage` is skipped whenever the `rust`
path filter is false. A site-only or docs-only push to `main` produces an attested, deployable
tarball with no Rust verification. Compounding: `config/toolforge-capacity.json` is **not** in the
`rust` filter, so a capacity-config-only change ships unverified — the exact file that governs
admission.

**Fix:** add `- 'config/**'` to the `rust` filter; require `coverage == 'success'` for `main` pushes.

### P1-11 · `.aethyme/` is not gitignored, and contains a SQLite broker DB + an unannotated file
`.gitignore:2-3` covers `/.chau7/` and `/.claude/` only. `.aethyme/` has no entry and currently
holds `broker.db`, `broker.db-shm`, `broker.db-wal`, `logs/`, `generated/`, and `gates.toml`.
`gates.toml` is generated by an external tool and carries no REUSE annotation — a `git add -A`
would fail the `reuse lint` gate in `security-node`. One-line fix.

## 6. Minors (P2) — grouped

**Resource / capacity**
- `compaction.rs:27-32` — 192 MiB target, full `vstack` + `maintain_order(true)` sort, **no
  governor**. 192 MiB of Zstd → 1–2 GiB resident; the sort transiently doubles it.
- `WEEKLY_BUCKET_ESTIMATED_BYTES_PER_ROW = 256` is the *only* memory model;
  `writer_bytes = writer_limit × 1 MiB` is a bare guess, and the 3 weekly routing writers set **no**
  `with_row_group_size` (unlike the 5 other writers in the codebase, which all do).
- `checkpoint()` failure aborts the whole stage — no backoff, no shrink, no retry. The only
  adaptive behaviour anywhere shrinks the wave on *admission* failure, never on *checkpoint* failure.
- FD budget silently disappears when `/proc/self/fd` is unreadable — every consumer is
  `if let Some(..)`, so the writer limit becomes unconstrained. Make it mandatory on Linux.
- `SMALL_MAX_HISTORICAL_MEMORY_BYTES = 4_500_000_000` is decimal-mixed among binary siblings and
  has no relationship to the 6 GiB envelope. Add an assertion against the config.
- `WIKI_ECON_COMPACTION_TARGET_BYTES` is settable but set by **no** wrapper.
- `capacity-admission.cjs:249` — a signal-killed child is reported as exit 1, not 128+signo, so an
  OOM-killed stage is indistinguishable from a logic failure.
- No OOM classification anywhere: SIGKILL is untrappable, so `run-record.cjs finish` never runs and
  the peak evidence is lost exactly when it matters. Read `memory.events` `oom_kill` counters in the
  existing 15 s sampler.

**Correctness**
- `src/orchestration.rs` (1 104 lines, all CLI dispatch) has **zero** `#[test]`.
- The stage-fingerprint cache key is `CARGO_PKG_VERSION` alone (`fingerprint.rs:570`); CI enforces
  version bumps for 4 of ~14 versioned stages. A forgotten bump silently reuses a stale artifact.
- `compute/mod.rs:2028` — `if wiki == "enwiki"` is a wiki-name branch. It should be a
  profile/capacity predicate, or the parametric design leaks.
- `prepare`'s failure path (`publication.rs:5722-5733`) omits the re-merge fallback that `rollback`
  has (`:5752-5763`), converting a self-healing state into a manual one.
- Family constants live in 3 places (`metric_registry.rs:151`, `compute/mod.rs:81`, `:1147`).
- `atomicWriteJson` re-implemented 6× across Node, 17× across Rust, with different durability
  properties (only the `admin-lifecycle.cjs` one `fsync`s the parent directory).
- The wiki set is duplicated in 4 unchecked places.

**Docs (all verified against source)**
- `docs/development.md:101-140` misdescribes CI on every count — job count, filter name, filter
  contents, and it omits `toolforge-release`. The test lists in `development.md:27-32` and
  `README.md:151-159` ("Equivalent expanded commands") name tests CI does not run.
- `docs/architecture.md:352` lists `cargo test` as a CI gate; it is skipped by design and is itself
  conditional.
- `docs/production-topology.md:68-70` + `deploy/toolforge/README.md:94-96` list 16 wikis;
  `config/wiki-lifecycle.json` has 18 (16 + `dewiki` + `enwiki`). The topology doc also omits all
  six `wiki-econ-pipeline-*` jobs.
- `docs/operations-recovery.md:84` documents `local-import` backup for elwiki/svwiki; both are now
  `toolforge`/`scheduled` — `create-imported-backup.sh` would produce an **empty archive**.
- `docs/resource-governor.md:102` documents `large` source workers as 3; code says 4.
- `docs/stack-and-data-sources.md:90` says "bounded to 4 concurrent downloads"; the max is 2.
- `docs/frontend-scalability.md:33` ("decoded rows retained only for the currently selected wiki")
  is **false** for the All-wikis path, which decodes every overlapping global shard at once.
- There is **no version-controlled required-checks config** — `docs/release.md:67-72` tells you to
  "keep branch protection enabled" in the UI, so required check names drift invisibly.

**Agility**
- `npm` caching is explicitly disabled in all 5 `setup-node` calls (defensible given the supply-chain
  posture, but a deliberate ~5× registry hit per PR).
- The 52 `node --test` invocations are serial in one `run:` block; `quality-node` has a 30-minute
  budget for them. Replace with a glob (P0-5) and add concurrency.
- `--all-features` is a no-op — `Cargo.toml` has no `[features]` table.

## 8. What is genuinely excellent — do not regress these

Audits that only produce findings hide what works. This repo is doing several things better than
most projects of any size, and the pressure of the enwiki effort is the kind of thing that erodes
them:

- **The publication gate chain.** 16 fail-closed gates, verified in `publish-ready-transaction.sh`
  and `publication::validate`, with `publication-verify` running **both before and after** the site
  build, immediately before the atomic symlink switch. Recovery is an explicit 9-state machine,
  not a best-effort retry.
- **Release provenance.** Sigstore attestation verified *independently on both ends*, plus
  checksum, ELF-arch, 8-member allowlist, `sha256sum --strict`, three CycloneDX SBOMs whose
  `artifact_sha256` must equal the release binary's own digest, and byte-comparison against any
  existing immutable release. This is genuinely best-in-class.
- **Determinism as a machine-checked contract.** `determinism.rs` embeds
  `config/determinism-contract.json` into every publication gate, so provenance is verifiable offline.
- **Generated-doc drift protection.** `generate-stack-reference.cjs:275-298` walks every hand-written
  doc and *fails CI* on any `x.y.z` version appearing next to a dependency name. That is why the
  stale doc items found here are all structural (job lists, wiki counts) rather than version drift.
- **Vendor patch governance.** `check_vendor_patches.cjs` cross-references
  `config/vendor-patches.json` ↔ `Cargo.toml` ↔ `cargo metadata` ↔ each `PATCHES.md`, with
  count equality enforced both ways. Better than almost any project.
- **Credential hygiene.** A full sweep found no credentials — one test fixture, upstream AWS doc
  examples, and `change-me` placeholders behind a documented render step.
- **The resource governor's *design*.** Predictive admission-before-allocation, RAII permits,
  fail-closed on missing Linux telemetry, real spill-to-disk in page-week and lifecycle, streaming
  merges at bounded batch sizes, `fadvise(DONTNEED)` on consumed row-group ranges. The architecture
  is right. The problems in §4/P1 are wiring, defaults, and arithmetic — all cheaper to fix than
  the design is to rebuild.

## 10. Corrections made during implementation (PR #105)

Three audit claims did not survive verification. Recorded here because the
grade card above is otherwise misleading.

**The shellcheck finding was wrong and is retracted.** The audit and a commit
both claimed the CI shellcheck step checked zero files, on the grounds that
`ludeeus/action-shellcheck` discovers scripts with `find -type f ! -name '*.*'
-perm /111`. That is not the pinned action's behaviour: its *first* `find` runs
`-type f ... -o -name '*.sh'`, which is how all 63 scripts are collected. The
`! -name '*.*' -perm /111` pass is a *second* find that only adds extensionless
executables and matches nothing here. The `additional_files` change was
reverted.

The tree genuinely was not shellcheck-clean (19 findings at default severity),
so that work was kept in a corrected form: a `.shellcheckrc` with a reason per
category, and the one false positive (SC2154) fixed inline. That is what makes
the new local shellcheck pass in `ci-local.sh` meaningful.

**Unresolved discrepancy.** CI reports that step as *passing* on `main`, while
the same tree fails locally at default severity with shellcheck 0.11.0. The
action downloads a floating `stable` build, so a version difference is the
likely explanation, but it was not confirmed. Someone with a Linux runner
should check whether the action's `stable` differs from 0.11.0. Not claimed as
fixed.

**The `.aethyme/gates.toml` REUSE risk was wrong.** It is already tracked, and
`REUSE.toml` has a blanket `path = "**"` annotation, so the `reuse lint` gate
was never at risk. The gitignore entry still stands, for the untracked broker
database and WAL.

**The CPU gates are not mutually exclusive.** The audit called
`qualify-capacity.cjs` (requires `cpu === 1`) and `cpu_qualification.rs`
(requires `cpu > 1 && speedup >= 1.15`) contradictory. They are sequenced: the
matrix gate *selects* a profile, an operator records it in
`capacity-qualification.json`, and the capacity benchmark then confirms at that
setting. Only the schema-version mismatch was a real bug, and only that was
fixed.

**`config/generated/metric-catalog.json` in the `site` filter** is real but
minor; unchanged.

## 11. Follow-up finding from implementing progressive publication (PR #108)

Adding per-wiki deferral surfaced something the audit did not reach, and it
changes what can safely be deferred.

**Two of preflight's per-wiki blockers are unreachable by construction.**

1. `record_candidate_fingerprint_drift`'s failure arm. It authenticates the
   candidate's artifacts via `artifact_backed_family_proofs`, but
   `ready_from_reference` has already authenticated those same artifacts
   moments earlier in the same loop iteration. Verified empirically: corrupting
   a `PerWikiOnly` artifact (`page_weekly_edits`) after a candidate is marked
   ready is caught by `ready_from_reference`, so control never reaches the
   later check.
2. `record_candidate_merge_contract`'s cross-wiki conflict. The contract it
   compares is derived from receipts that `ready_candidate_merge_contracts` has
   already pinned to `metric.definition().algorithm_version` and the declared
   schema. Two published wikis therefore *always* produce identical contracts,
   and the conflict it guards against can never be constructed from real data.

Both are defence-in-depth against a future relaxation of those validations, not
live failure modes. They are better read as integrity invariants than as
readiness checks — which is the line PR #108 draws:

> **Readiness defers. Integrity does not.**

Deferred (per-wiki readiness): unreadable ready index, invalid ready-index
identity, candidate authentication failure, invalid candidate merge contract.

Never deferred (global blockers in both modes): snapshot downgrade,
stable-version fingerprint drift, cross-wiki merge-contract conflict, and
recovery / scrub / gate failures — each of which would publish something wrong
or keep serving stale data rather than merely skip a wiki.

**Consequence for P1-4.** The audit's "a hard-killed publisher blocks
publication for up to 6 hours, invisibly" is a *scheduling* problem, not a
correctness one, and deferral does not address it. It remains open.
